| ---- | -------------------------- | ---------------------------------------------------------------- |

| 5.3  | `adjustUIBy`               | 이름을 **UI 조정**이라는 호출부 의도 수준으로 일반화(2차 추상화) |

## 의도 vs 구현

도서에서 말하는 **의도 vs 구현**은 "의도가 없다"는 뜻이 아니라, **어느 층(level)의 의도를 이름에 담았는가**의 차이이다.

### 이벤트 리스너가 위임하려는 일 (높은 층)

```javascript
$filter.addEventListener('change', ({ target }) => {
  // "필터 값이 바뀌었으니, 화면을 그에 맞게 맞춰라"
  ???(target.value);
});
```

리스너의 본질은 **"필터 변경 → UI 상태 동기화"** 이다.

### `adjustOrdersAndFiltersBy` (낮은 층 — 구현에 가까운 의도)

- **"정렬(order)과 필터(filter)를 조정한다"** 는, 화면 **구성 요소(부품)** 를 이름에 박아 둔 의도
- 함수 내부에서 만지는 대상의 **종류(정렬, 필터)** 와 이름이 1:1로 맞물림 → **인터페이스 면적이 넓다** (ch-04)

### `adjustUIBy` (높은 층 — 호출부의 본질)

- **"필터 값에 따라 UI를 맞춘다"** — 리스너가 하려는 일과 **같은 층**에서 말함
- 검색창, 안내 문구 등 UI 대상이 늘어나도 이름이 유지됨

## 정리: 둘 다 "의도"지만 층이 다르다

|                 | `adjustOrdersAndFiltersBy`        | `adjustUIBy`                  |
| --------------- | --------------------------------- | ----------------------------- |
| 의도의 층       | **무엇으로** 맞추는지 (정렬·필터) | **무엇을** 맞추는지 (UI 전체) |
| 호출부와의 관계 | 리스너보다 **더 구체적**          | 리스너와 **같은 수준**        |
| 새 UI 추가 시   | 이름이 **거짓**이 될 수 있음      | 이름 **유지** 가능            |

> `adjustOrdersAndFiltersBy`도 의도는 맞지만, **"정렬·필터"라는 화면 구성 요소**를 이름에 박아 둔 의도이고, `adjustUIBy`는 **"필터 바뀌면 UI를 맞춘다"** 는 그 자리(호출부)의 본질을 이름에 담은 것이다.

## 실무 기준

### 5.2가 나쁜가?

- **나쁜 코드가 아님** — 범위가 좁고 안정적이면 1차 추상화로 충분
- **한계** — 다루는 UI가 늘어나면 이름과 실제 역할이 어긋남

### 어디까지 추상화?

- **미래를 전부 예측하지 않는다** (YAGNI)
- **이름이 더 이상 하는 일을 설명하지 못할 때** 한 단계 올린다

### 이름을 올릴 신호

1. 함수 이름에 없는 대상을 수정하기 시작했다
2. "이 함수는 ○○만 한다"고 설명하기 어려워졌다
3. filter value별 UI 조정 로직이 계속 커진다

### 네이밍 원칙

- **호출부**: 의도 수준 (`adjustUIBy`)
- **함수 내부**: 구체적 (`disablePriceSort`, `hidePointNotice`)
- **너무 추상적** (`handleChange`, `process`)은 피한다

### 추상화

추상화란 **복잡한 정보에서 필요한 부분만 남기고 단순화하는 과정**을 말한다. 추상화는 코드를 함수로 분리하는 과정으로 볼 수 있다. 함수로 분리하는 과정에서 if 문을 사용하고 요소의 disabled 속성에 불리언 값을 할당하는 구체적인 방법 등은 숨겨진다. 대신 **함수 이름**과 **매개변수**처럼 **꼭 필요한 정보**만 남게 되는데, 이것이 바로 추상화이다.

한걸음 더 나아가, 외부 코드를 기준으로 보면 이전에는 구체적인 코드에 의존했다면 추상화 이후에는 함수에 의존하게 된다. 즉 추상화 이후에는 외부 코드는 구체적인 코드가 아닌 인터페이스에 의존하게 된다. 예제 5.2나 예제 5.3에서는 함수 인터페이스를 수정하지 않는 한, 수정의 영향이 함수 내부로 한정된다.

결론적으로 **추상화는 정보를 선별하고 일반화하는 과정**이다. 그 결과, 정보를 사용하는 주체가 구체적인 코드가 아닌 **추상화된 인터페이스에 의존**하도록 만든다. 이로써 코드는 이전보다 더 유연해진다.

### 추상화 수준

추상화 수준이 높거나 낮다는 것은 저보의 선별 또는 일반화 수준을 의미한다. 즉 추상화 수준이 높다는 것은 일반화를 많이 했다는 것으로 이해할 수 있다. 위에서 말한 의도의 층과 같다.

> 추상화 수준의 다른 관점
> 이 도서에서는 "일반화 정도"를 기준으로 추상화 수준을 설명했지만 "추상화를 얼마나 잘했는지"를 두고 추상화 수준을 이야기하기도 한다. 이 관점에서 추상화 수준이 높다는 것은 추상화를 잘했다는 의미와 같다. 이때 잘된 추상화란 함수나 컴포넌트의 세부 구현을 효과적으로 숨기고 무엇을 하는지 명확하게 드러내는 것을 말한다.

추상화는 **가지고 있는 정보 중 상황에 따라 필요한 정보만 선별 또는 일반화하는 과정**이다. 또한 **정보를 선별하고 일반화할수록 추상화 수준은 높아지고 반대의 경우 추상화 수준은 낮아진다**

### 추상화 계층

위 예제는 추상화가 필요한 정보(인터페이스)만 남기고 불필요한 정보(내부 구현)을 제거함으로써 복잡한 문제를 단순하게 만든다는 사실을 보여준다. 이처럼 추상화, 인터페이스, 캡슐화는 모두 긴말하게 연관된 개념이다.

이처럼 추상화를 통해 알아야 할 정보와 몰라도 되는 정보를 나눌 때 생기는 경계를 추상화 계층이라고 한다. 각 계층은 상위 계층에서 알아야 할 정보만 노출하고, 하위 계층의 세부 사항은 상위 계층이 알지 못하도록 숨긴다.
