## 책 내용 기록

### 인터페이스

> "인터페이스는 서로 다른 두 개의 시스템, 장치 사이에서 정보나 신호를 주고받는 경우의 접점이나 경계면이다."

쉽게 풀어보면 인터페이스는 inter(사이)와 face(얼굴)로 나누어, "둘 사이에 위치하며 서로 마주하는 면"으로 볼 수 있다. 즉 인터페이스는 두 대상이 서로 만나서 소통하고 작용하는 공간이다.

- 인터페이스는 상호작용 방법을 알려주기 위해 공개된 부분이다. 즉 일종의 계약이라고 할 수 있다.
- 인터페이스를 준수하기만 하면 그 외의 사항에 대해 신경 쓸 필요가 없다. 기능을 개발하는 쪽과 인터페이스를 참고해서 기능을 사용하는 쪽 모두의 관심사는 인터페이스다. 즉 구현은 자유롭게 할 수 있다.

### 사용자 인터페이스 (User Interface)

프론트엔드 개발자의 중요한 역할 중 하나는 사용자에게 제공하는 서비스의 사용자 인터페이스를 만드는 것이다. 사용자는 이 UI를 기반으로 서비스를 이용하므로 사용자 인터페이스는 중요하다.

- 인터페이스로 `공개할 것과 공개하지 않을 것의 경계`를 명확히 해야한다. 외부로부터 접근할 수 있는 것과 `접근을 제한해야 하는 것을 신중하게 선정`해야 한다.

적절한 사용자 인터페이스는 신체적으로 장애가 있거나, 모바일 기기 등 다양한 기기로 접근하거나, 인터넷이 끊기거나, 안경을 잃어버리는 등 다양한 상황과 환경에서도 사용자가 서비스를 이용할 수 있는 방법을 제공해야 한다. 물론 이 모든 것을 항상 고려하기에는 한계가 있다. 하지만 사용자가 애플리케이션과 상호작용하는 데 제한이 있다면 `지속적인 노력`을 통해 모든 사용자가 원활하게 서비스를 이용할 수 있도록 하는 것이 중요하다

### 함수와 인터페이스

프론트엔드 개발에 사용하는 함수에도 인터페이스가 있다. 함수 이름, 매개변수, 반환값은 함수를 파악하고 사용하기 위한 규칙, 즉 인터페이스다.

> [!NOTE]
> `시그니처란?` 함수의 이름과 매개변수, 반환값은 시그니처라고 하며 함수의 사용법을 설명하고 다른 함수와 구별할 수 있도록 하는 개념을 말한다. 시그니처는 함수를 다른 함수로부터 유일하게 구별하는 정보인 반면, 인터페이스는 여러 함수가 공통으로 구현해야 하는 구조를 추상화함으로써 이를 구현하는 함수들을 하나의 추상화된 개념으로 이해할 수 있도록 하는 정보를 말한다.

#### 예제 과정 `book-examples/ch-02/01.js`

각 로직이 어떤 데이터를 필요로 하는지, 각자의 관점에서 명확히 정의해보자. 또한 각 로직이 어떤 역할을 수행하는지, 어떤 값을 반환하는지도 함께 정의하자.

인터페이스가 잘 정의되어 있으면 세부 구현을 보기 전에도 코드의 역할과 사용법을 빠르게 파악할 수 있다. 경우에 따라서는 구현을 전혀 보지 않고 인터페이스만 이해하는 것으로도 충분하다.

반대로 함수를 분리하지 않으면 로직 간 결합도가 높아질 가능성이 크다. 하지만 인터페이스를 제외한 내부 구현이 캡슐화되어 있으면 세부 로직의 결합이 제한된다. 즉 구현이 아닌 추상에 의존하도록 만드는 과정이라고 볼 수 있다.

#### 인터페이스의 중요성

1. 함수를 구현하기 전에 인터페이스를 먼저 고민하고 만듦으로써 함수가 다른 주체들과 어떤 관계를 맺고 협력해야 하는지 먼저 고민하게 한다.
2. 인터페이스를 기반으로 전혀 다른 구현을 적용할 수 있도록 한다.

### 단일 구현을 위한 인터페이스

인터페이스와 인터페이스를 준수하는 구현이 하나씩 존재하는 경우 이 인터페이스를 단일 구현을 위한 인터페이스를 말한다.

```ts
// 인터페이스와 함수 구현이 모두 존재
type Sum = (a: number, b: number) => number;
const sum: Sum = (a: number, b: number) => a + b;

// 명시적인 인터페이스 없이 구현만 있는 경우
const sum = (a: number, b: number) => a + b;
```

보통 인터페이스를 따로 만들지 않는다. 이렇게 하는 이유 중 하나는 코드 전반에 있는 함수의 개수를 따져보면 함수마다 인터페이스를 만들고 관리하는 것은 무시할 수 없을 정도의 큰 비용이 들기 때문이다. 또한, 인터페이스를 구현체들이 공통적으로 준수하는 규칙으로 이해한다면, 구현체가 하나일 때의 인터페이스는 다른 구현체가 추가될 때 변경될 가능성이 높다. 따라서 인터페이스와 구현체가 각각 하나인 경우 인터페이스를 구현체가 있는 곳에 위치하는게 좋다. 시점 이동없이 한 눈에 볼 수 있기 때문이다.

### 테스트와 인터페이스

테스트 환경에서 인터페이스는 테스트하려는 대상을 제외한 나머지 구현을 교체할 수 있도록 도와준다. 이렇게 하면 테스트 대상이 의존하는 불필요한 주변 요소를 제거하고 효과적으로 테스트를 수행할 수 있다.
