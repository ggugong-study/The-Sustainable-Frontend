# 의존성

## 핵심 개념

- 의존성은 `하나의 요소가 다른 요소의 변경에 영향을 받는 관계`를 의미한다.
- 의존성 종류에는 변수, 함수, 타입, 불변속성 의존성이 있다.
- 의존성은 의존 여부를 나타내고, 방향성을 나타낸다. 결합도는 의존의 강도를 나타낸다.
- 의존성 역전과 의존성 주입을 통해, 결합도를 느슨하게 만들고 의존 방향을 제어할 수 있다.

## 책 내용 기록

### 의존성(Dependency)

의존성이란 어떤 대상이 동작하기 위해 다른 대상을 필요로 하는 상태를 말한다. 의존성은 의존 여부를 설명할 때 사용하고, 방향에 대한 속성을 갖고 있다.

### 결합도(Coupling)

결합도는 두 대상이 서로 의존하는 정도를 나타낸다. 그래서 "결합도가 강하다"와 같이 사용한다. 따라서 의존하고 있는 두 대상의 결합도의 정도가 강할수록 조그마한 수정이 치명적일 수 있다.

---

아무리 별거 없어보이는 의존성이라도 잘 관리하지 않으면 복잡도가 높고, 수정하기 어려운 코드가 된다. 코드를 수정할 때 간단하게 수정할 수 있을 거라 생각했지만, 막상 코드를 들여다보면 그렇지 않을 때가 있다. 따라서 의존성 관리가 잘되어 있는지 점검할 필요가 있다. 왜냐하면 `의존성은 관계뿐만 아니라 변경에도 영향을 미치기 때문이다.`

변경 가능한 범위가 넓다면 의존하고 있는 코드 변경 시 다른 곳의 변경으로 전파될 가능성을 만든다.

### 변수 의존성

변수는 만들고 다루기 쉽지만, 오히려 그렇기 때문에 복잡한 의존 관계로 인한 복잡도가 발생할 가능성이 높다.

- 변수에 접근 가능한 스코프를 제한하여, 변경의 영향을 최소 범위로 한정하자.

### 함수 의존성

함수도 변수와 마찬가지로, 처음에는 단순한 유틸리티 함수였더라도 시간이 지나며 점차 복잡한 책임을 갖게 될 수 있다. 또한 함수를 사용하는 모든 곳은 해당 함수의 동작과 인터페이스에 의존하게 된다. 컴포넌트도 마찬가지로 시간이 지날수록 속성과 조건문이 추가되면서 수정하기에는 몸집이 너무 커지는 현상이 생긴다. 이 같은 형태의 의존성 문제를 ㅎ개ㅕㄹ하는 방법 중 가장 유명한 한 가지 방법은 `의존성 역전(Dependency Inversion)`이다.

함수를 사용할 때 의존성 문제로 코드가 스파게티처럼 꼬여 있다면 `의존성 역전`을 고려해볼 수 있다.

### 인터페이스

인터페이스는 서로 메세지를 주고받는 대상이 정한 규칙 또는 계약과 같다. 자바스크립트에서 `parseInt`는 '문자열을 전달하면 숫자를 반환한다'라는 규칙, 즉 인터페이스를 지키고 있다고 말한다.

> [!NOTE]
> 타입스크립트를 사용하면, 인터페이스를 IDE 단계에서 강제할 수 있다.

```text
[사용자 입력]
     │
     ├───────────────────────────────┐
     │                               │
     ▼                               ▼
[전화번호 입력 이벤트 리스너]      [가격 입력 이벤트 리스너]
     │                               │
     │ getNumber() 의존               │ getNumber() 의존
     └───────────────┬───────────────┘
                     ▼
               [getNumber 함수]
```

위 코드를 `의존성 역전`을 사용하면 다음과 같은 흐름이 나온다.

```text
                    [getNumber] (또는 다른 parser)
                               │
                               │ 주입
                               ▼
                  [parsePhoneNumber(value, parser)]
                               ▲
                 의존(호출 위임) │
         ┌─────────────────────┴─────────────────────┐
         │                                           │
         │ 의존                                      │ 의존
         ▼                                           ▼
[전화번호 입력 이벤트 리스너]                [가격 입력 이벤트 리스너]
         ▲                                           ▲
         └─────────────────────┬─────────────────────┘
                               │
                            [사용자 입력]
```

`book-examples/ch-01/index.ts`예시와 같이 `Parser` 인터페이스는 실제 함수를 사용하는 쪽에 위치하는것이 좋다. 사용하는 곳에서 관리한다는건 인터페이스를 따르는 범위에서 함수 내부 구현의 독립성이 보장된다. 즉 상위 모듈의 변경 없이도 내부 로직을 자유롭게 변경할 수 있다.

### 타입 의존성

타입스크립트를 사용하는 환경이 많아지면서, 타입 의존성을 어떻게 관리할 것인지도 중요한 설계 요소가 되었다. 예를 들어 API Response 타입을 하나 정의한 뒤 여러 곳에서 그대로 사용하는 방식보다, 도메인 기준으로 타입을 분리하는 방식이 더 안정적일 수 있다.

그 이유는 API 응답 구조는 비교적 자주 변경될 수 있지만, 핵심 도메인 규칙은 상대적으로 쉽게 변하지 않기 때문이다. 도메인 규칙이 변경된다면 프론트엔드와 백엔드 모두 함께 수정해야 할 정도로 영향 범위가 크다. 따라서 외부 응답 형태에 직접 의존하기보다, 내부에서 사용하는 도메인 타입을 별도로 정의해두는 편이 변경에 강한 구조를 만든다.

물론 타입의 개수와 변환 과정은 늘어날 수 있다. 하지만 Response 타입과 도메인 타입을 분리하면 각 계층의 역할이 명확해지고, 여러 곳에 흩어진 암묵적인 도메인 규칙을 하나의 타입으로 묶을 수 있다. 결국 단순한 타입 분리가 아니라, 중복된 도메인 표현을 제거하고 의존성의 방향을 통제하는 과정으로 볼 수 있다.

### 불변속성 의존성

불변속성(invariant)은 코드가 실행되는 동안 항상 만족하도록 보장해야하는 규칙을 말한다. 비즈니스 규칙인 경우 애플리케이션 전체를 통틀어 일관성 있게 유지되어야 한다. 즉 애플리케이션 전체가 의존하거나 의존할 가능성이 존재한다. 불변속성뿐만 아니라 함수, 컴포넌트 등의 매개변수, 반환값으로 보이지 않는 내부 정보를 암묵적으로 참고해서 작성한 코드는 보이지 않는 정보에 의존하기 때문에 매개변수와 반환값의 구조 및 형태가 바뀌지 않더라도 변경에 취약할 수 있다.

```js
// before
let accountBalance = 1000;

if (accountBalance >= 0) {
  // ...
}

// after
// account.js
export function isBalanceValid(balance) {
  return typeof balance === "number" && balance >= 0;
}

// index.js
let accountBalance = 1000;

if (isBalanceValid(accountBalance)) {
  // ...
}
```

위와 같은 방식으로 작성된 코드는 괜찮아 보이지만, 코드 전반적으로 흩어져있을 때 관리하기가 어렵다. 따라서 한 곳에서 불변속성을 관리하는 것이 좋다. 데이터 또는 로직에 대한 진실의 원천이 하나여야 하는 것처럼, 불변속성 또는 비즈니스 정보를 한 곳에서 관리하고 필요시 참조할 수 있도록 해야 변경으로 인한 영향을 최소화할 수 있다.

```js
// before
// 불변속성 - "장바구니에 담긴 상품 배열(items)은 항상 가격이 낮은 순서대로 정렬되어 들어온다"는 규칙이 있다.
interface CartItem {
  productId: string;
  price: number;
}

// 외부에서 '가격 오름차순'으로 정렬해왔다는 보이지 않는 정보에 의존함
export function calculateDiscount(items: CartItem[]): number {
  if (items.length === 0) return 0;

  const cheapestItem = items[0]; // 💥 암묵적 의존성 포인트
  return cheapestItem.price * 0.5;
}

// after
export function calculateDiscount(items: CartItem[]): number {
  if (items.length === 0) return 0;

  // 외부 정렬 상태와 관계없이, 자신의 비즈니스 규칙은 내부에서 직접 보장
  const cheapestItem = items.reduce((cheapest, current) =>
    current.price < cheapest.price ? current : cheapest
  , items[0]);

  return cheapestItem.price * 0.5;
}
```

### 의존성 역전

상위 수준의 모듈(비즈니스 로직)이 하위 수준의 모듈(구체적인 기술이나 도구)에 의존해서는 안 되며, 양쪽 모두 추상화(인터페이스)에 의존해야 한다는 객체지향 및 소프트웨어 설계 원칙이다.

### 의존성 주입

함수나 클래스가 내부에서 사용할 다른 객체(의존성)를 스스로 생성하지 않고, 외부(제3자 또는 호출자)로부터 필요한 객체를 매개변수 등을 통해 밀어 넣어주도록 만드는 구체적인 구현 기법이다.

## 📝 읽고 나서 든 생각들

코드 설계라는 말이 정확히 무엇을 하는건지 잘 몰랐었다. 의존성과 결합도가 무엇인지에 대해 배우고 또, 다양한 의존성들을 배우면서 도움이 정말 많이 되었다. 특히 의존성 역전(DIP)가 인상적이였다. 내가 알던 콜백은 본질적인 의미로 "사용자와 상호작용 하기 위해" 정도만 알고있었기에 설계적인 콜백 함수를 사용할 일이 크게 많지 않았다. 하지만 이 책에서는 상위 모듈과 하위 모듈이 인터페이스라는 규칙을 바라보도록하여 의존성을 역전한 예제를 그림과 함께 제공했는데, 이것을 보고 머리에 무언가 스치듯 지나가면서 깨달은 느낌(?)이 들었다.

앞으로 함수 및 컴포넌트 등을 설계할 때 `의존성`, `결합도`를 다이어그램을 그리면서 의식적으로 연습해보려고 한다. 책 내용 너무 좋고, 공부 많이 된다👍👍
