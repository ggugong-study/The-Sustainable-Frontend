# 캡슐화

## 책 내용 기록

### 캡슐화란

캡슐화는 서로 관련있는 데이터와 함수를 하나로 묶고, 외부에는 정해진 방법(인터페이스)으로만 접근하도록 제한함으로써, 내부를 보호하는 방법을 말한다. 즉 외부와 내부를 명확히 구분함으로써 내부의 변경이 외부에 미치는 영향을 최소화한다.

> [!IMPORTANT]
> 캡슐화를 언제, 어떻게 활용할 수 있을지 함께 고민해 본다면 코드의 안정성과 유지보수성을 높이는 데 많은 도움이 된다.

### 캡슐화와 스코프

변수나 함수를 특정 스코프 내부에 숨기면 외부에서 접근할 수 없게 되므로 이들은 해당 스코프 안에서 자유료워진다. 다시 말해, 내부에 숨겨진 대상을 수정하거나 삭제하더라도 외부에 영향을 주지 않을 수 있다. 반면 모든 변수와 함수가 하나의 스코프에 있다면 이름이나 값을 바꾸는 등의 변경이 다른 코드에 의도치 않은 영향을 줄 가능성이 있다.

캡슐화를 통해 변경의 영향을 특정 영역으로 제한할 수 있다는 사실은 코드를 작성할 때 떠올릴 수 있는 중요한 아이디어를 제공한다. "변경이 예상되는 부분은 최대한 숨기는 것이 좋겠다" 또는 "외부에 노출할 필요가 없는 코드는 노출하지 말아야겠다"와 같은 생각이다.

데이터와 관련 로직을 한곳에 모으고 외부로부터 보호하면 내부 구현이 변경되더라도 인터페이스만 동일하게 유지된다면 외부에 미치는 영향을 제한할 수 있다.

스코프와 캡슐화는 외부와 내부를 구분한다는 점에서 깊이 연관되어 있다. 따라서 변수의 스코프를 다룰 때 캡슐화의 관점을 함께 고려한다면 코드의 구조를 더욱 견고하게 만들 수 있다. `인터페이스가 두 대상 사이의 소통 규칙을 정의`한다면 `캡슐화는 소통에 불필요한 정보를 숨기고 필요한 정보만 인터페이스를 통해 공개`하도록 하는 도구다.

### 함수를 사용한 캡슐화

데이터를 다루는 방법을 함수 내부로 캡슐화하여 인터페이스만 외부로 공개하여 사용할 수 있다. 로직을 여기저기 찾아다니지 않고, 해당 함수만 확인하면 된다. 또한 인터페이스를 변경하지 않는 한 내부 함수만 보면 된다.

### 클로저를 사용한 캡슐화

캡슐화와 의존성 등을 논의할 때 중요한 것은 `가능성`이다. 전역 변수를 다른 곳에서 쓰지 않는다고 해서 이런 상태를 무시해도 되는것은 아니다. 왜냐하면 다른 함수나 모듈이 이들에게 의존할 `가능성`이 존재하기 때문이다. 이는 마치 에러가 발생할 가능성을 가진 코드를 "지금 당장 문제가 발생하지 않으니까"라는 이유로 그대로 두는 것과 비슷하다.

이 문제는 미묘하다. 문제가 발생할 모든 가능성을 차단하며 코드를 작성하는 것은 비용을 요구하고 현실적으로 불가능하기 때문이다. 그렇다고 방치하면 작은 가능성이 쌓여 문제가 발생할 확률은 점점 높아진다. 문제가 쌓이기 전에 해결하는 것은 쉽지만 상당히 쌓이고 난 후에 해결하기란 어렵다.

- `book-examples/ch-03/closure-encapsulation.js`

### 클래스를 사용한 캡슐화

클래스를 사용하여 같은 목적을 가진 변수와 함수를 모으고, 외부에서 접근할 필요가 없는 경우 클래스 내부로 숨겼다. 이렇게 함으로써 이벤트 리스너에는 복잡한 로직 대신 선언적인 코드를 남기고, 클래스에서 발생하는 변경사항이 어디에 어떻게 영향을 줄지 파악하기가 수월해졌다.

- `book-examples/ch-03/class-encapsulation.js`

### 캡슐화를 해치는 경우

캡슐화를 적용한 후에는 그것을 깨뜨리지 않고 유지하는 것도 중요하다. 특히 캡슐화된 변수나 속성은 외부에서 접근하지 못하도록 더욱 주의해야 한다. 외부에서 직접 접근하고 수정할 수 있다면 해당 로직을 이해할 때 외부 코드까지 모두 살펴봐야 하므로 사실상 캡슐화를 깨뜨리는 것과 다름없다.

```js
class Counter {
  public count = 0;

  public increase(){
    this.count += 1;
  }

  public decrease(){
    this.count -= 1;
  }
}

const counter = new Counter()

const resetCount = () => {
  counter.count = 0
}
```

위와 같은 문제를 해결하거나 예방하려면 `객체의 속성은 숨기고, 외부에 공개한 행동(메서드)을 통해서만 접근하도록 제한`해야 한다. 그리고 `서로 관련 있는 속성(상태)과 메서드(행동)는 같은 객체(스코프) 안에 모아야` 한다. 이 둘이 서로 관련 있음에도 흩어져 있다면 코드를 수정할 때 흩어진 조각을 찾느라 많은 시간과 비용을 지불할 가능성이 높아진다.

캡슐화를 해치지 않기 위해서는 정보를 직접 사용하는 것이 아니라 책임을 가진 객체에 물어봐야 한다.

> [!NOTE]
> 디미터 법칙
> 이 법칙은 숨긴 정보가 외부로 노출되지 않는지 점검하는 방법을 제시한다. 따라서 디미터 법칙을 지킨다는 것은 내부 정보를 외부에 노출하지 않는다는 것을 의미하며, 외부에서 해당 정보를 가정해서 기능을 구현하지 않아야 한다는 뜻이다.

## 📝 읽고 나서 든 생각들

- 기존에 내가 알고 있던 캡슐화는 단순히 "내부 세부 구현을 감추는 목적"이었다. 하지만 이 챕터에서는 왜 그렇게 하는 것이 좋은지 알 수 있었다. 캡슐화는 인지적 부담을 줄이는 목적도 있지만, 더 중요한 것은 외부에서 내부 구현에 직접 접근하거나 의존할 가능성을 줄이는 데 있다.

다시 말해, 캡슐화는 `서로 관련 있는 데이터와 로직을 한곳에 모으고, 외부에는 정해진 인터페이스로만 접근하도록 제한함으로써 내부 구현의 변경이 외부에 미치는 영향을 최소화하는 방법`이라고 볼 수 있다.

- 외부 코드가 내부 구현을 직접 알수록, 내부 구현 변경은 외부 코드 변경으로 이어진다.
- 외부 코드가 공개된 인터페이스에만 의존할수록, 내부 구현은 자유롭게 바꿀 수 있다.

캡슐화란? 서로 관련있는 데이터를 하나로 묶고, 외부에는 정해진 인터페이스로만 접근하도록 하여 내부의 변경이 외부에 미치는 영향을 최소화한다.

## 질문

- 왜 외부에는 정해진 인터페이스로만 접근하도록 제한하여 내부 구현의 변경이 외부에 미치는 영향을 최소화하는걸까?
  - 적절한 인터페이스로 접근을 제한하지 않으면, 외부 코드가 내부 데이터 구조나 구현 방식에 직접 의존하게 되기 때문이다.
- 내부 데이터에 의존하면 왜 안되는건데?
  - 외부 코드가 내부 구현을 알고 있는 만큼, 내부 구현을 변경할 때 외부 코드도 함께 수정해야 할 가능성이 커지기 때문이다.
- 인터페이스를 사용한다고해서 영향이 가는건 마찬가지 아니야?
  - 인터페이스 자체를 변경하면 외부에도 영향이 간다. 하지만 인터페이스를 유지한 채 내부 로직만 변경한다면, 변경 범위를 캡슐화된 내부로 제한할 수 있다.
